## О проекте

Я заметил, что в каждом новом проекте для **AVR** копирую один и тот же код: настройка пинов, задержки, работа с EEPROM, дисплеями. Вместо того чтобы делать это в десятый раз, я собрал все наработки в одну **header-only** библиотеку

Фокус на том, чтобы код был **читаемым** и **безопасным**, но компилировался в такой же **оптимальный ассемблер**, как и **чистый C**

Никаких виртуальных функций, RTTI или исключений - только **статический полиморфизм на шаблонах** и **агрессивный инлайнинг**

## Возможности

| Модуль                    | Файл                     | Шаблон/Структура                                                   | Что умеет                                                         |
|---------------------------|--------------------------|--------------------------------------------------------------------|-------------------------------------------------------------------|
| **Задержки**              | `Delay.h`                | `FDelay`                                                           | Задержка в Тактах/Микросекундах/Миллисекундах на этапе компиляции |
| **Цифровые пины**         | `GPIO/Pin.h`             | `TPin<uint8 InPin>`                                                | Работа с цифровыми пинами AVR (Arduino мапппинг)                  |
| **Кнопки**                | `GPIO/PinButton.h`       | `TPinButton<uint8 InPin>`                                          | Опрос с подтяжкой + Флаги состояний                               |
| **PWM**                   | `GPIO/PinPWM.h`          | `TPinPWM<uint8 InPin, bool bInverted>`                             | ШИМ на аппаратных таймерах                                        |
| **Последовательный порт** | `Communication/Serial.h` | `FSerial`                                                          | UART с фиксированной скоростью                                    |
| **I2C**                   | `Communication/TWI.h`    | `FTWI`                                                             | TWI (Two-Wire Interface)                                          |
| **EEPROM**                | `Memory/EEPROM.h`        | `FEEPROM`                                                          | Чтение/запись                                                     |
| **PROGMEM**               | `Memory/PROGMEM.h`       | `FPROGMEM`                                                         | Работа с данными во Flash                                         |
| **LED-матрицы**           | `Display/MAX7219.h`      | `TMAX7219<uint8 InDIO, uint8 InCS, uint8 InCLK, uint8 InSize = 1>` | MAX7219                                                           |
| **OLED**                  | `Display/OLED.h`         | `TOLEDtemplate<uint8 InAddress = 0x3C>`                            | SSD1306                                                           |

## Быстрый пример

```cpp
#include "AAT/GPIO/Pin.h"
#include "AAT/Delay.h"

using MyLedPin = TPin<13>;

int main()
{
    MyLedPin::InitializeAsOutput();
    
    while(true)
    {
        MyLedPin::Toggle();
        FDelay::Milliseconds<1000>();
    }
}
```

**Сравнение с Arduino Blink _(ATmega328P)_:**

|                      | **Arduino** | **AAT**       |
|----------------------|-------------|---------------|
| Flash (.text)        | 924 байт    | **139 байт**  |
| RAM (.bss)           | 9 байт      | **0 байт**    |
| RAM (.data)          | 0 байт      | **0 байт**    |
| **Итоговый размер**  | 933 байта   | **139 байт**  |

**Flash** меньше в **6.6 раза**, а **RAM** вовсе не занята

## Project Template

Также в репозитории есть папка `Project Template` - готовая структура для нового проекта

### Как использовать

1. Скопировать папку `Project Template` под новым именем
2. (При необходимости) отредактировать `CMakeLists.txt` - указать тип МК, частоту, порт и тд.
3. Запустить `Build.bat`

**Что делает `Build.bat`:**
- Копирует `AAT` из `Include/` в папку проекта
- Запускает **CMake** с предустановленными параметрами
- Создает `.sln` проект в папке `Build`
- Через **CMake** генерирует `Upload.bat` для загрузки кода в МК
- **Самоуничтожается**

После сборки можете писать код и запускать `Upload.bat` для прошивки МК

_(`Build.bat` срабатывает только один раз, чтобы случайно не перезаписать ваши изменения. Дальше используйте **CMake** напрямую!)_

### Как подключить вручную (без шаблона)

1. Скопировать папку `AAT` из папки `Include/` в свой проект
2. Собрать с флагами:
   ```
   -std=c++17 -fno-exceptions -fno-rtti -Os
   ```

### Примечания

Для комфортной работы в средах разработки, которые не поддерживают **AVR-специфичные расширения**, был добавлен макрос `__IDE__`

Он позволяет подменять конструкции, непонятные IDE, на нейтральные заглушки - без влияния на реальную компиляцию (в боевом коде макрос не определен)

**AAT/Core/Aliases.h**
```cpp
#ifdef __IDE__

// Грязный хак, позволяющий IDE не жаловаться на конструкции, специфичные для AVR
#define F_CPU 0
#define __extension__
#define __volatile__
#define __DOXYGEN__
#define __AVR_ATmega328__

#endif
```
Это не влияет на итоговый код - лишь простой способ сохранить подсветку, автодополнение и чистый лог ошибок в IDE

## Почему **Advanced AVR Templates**, а не **Arduino**?

**Arduino** удобна для прототипирования, но ее цифровые пины, `delay()`, `Serial` и тд. имеют очень большие накладные расходы _(проверки, косвенные вызовы)_

**Advanced AVR Templates** дает такой же удобный интерфейс, но с нулевой стоимостью абстракций - компилятор агрессивно инлайнит, генерирует прямые `SBI`/`CBI` инструкции и рассчитывает все константы заранее _(Compile-time вычисления)_

## И на последок

**Advanced AVR Templates** создана именно для **боевых условий** - когда **каждый байт ОЗУ на вес золота**, а **косвенные вызовы**, **переполнение стека** и **перетирание данных** становятся критической проблемой

Все началось с проекта на микроконтроллере с **1 КБ RAM**. Проблема в том, что **стек растет вниз** _(или вверх - зависит от архитектуры)_, а статические переменные, хоть и лежат внизу, но "выдавливают" свободную память под стек

И достаточно глубокого вызова, и стек начинает затирать эти переменные _(или переменные перетирают стек)_

Стандартные подходы Arduino с вызовом функций внутри функций, промежуточными локальными переменными и указателями на функции лишь усугубляли ситуацию: косвенные вызовы = лишние адреса в стеке = больше вложенность = выше риск перетирания

Пришлось писать свой ~~велосипед~~ библиотеку

### Основные принципы

- Минимум RAM - в идеале 0 байт
- Минимум косвенных вызовов - никаких виртуальных функций и указателей на функции
- Минимум глубины стека - чтобы не приближаться к статическим данным
- Всё, что возможно - на этап компиляции _(шаблоны, constexpr, if constexpr, static_assert)_

И да, конечно шаблоны и инлайнинг не по-детски увеличивают **Flash**. Но обычно **Flash** на порядок больше, а вот **RAM** - нет. Поэтому:

> **"Тяжело в компайле - легко в рантайме"**
